DECISIONS
- Motion model: STRAIGHT LINE ALONG X ONLY, signed speed (positive = forward, negative =
  backward, 0 = stopped). The vehicle is a 1 m cube; a cube's orientation cannot be read
  from its shape, so there is no yaw and no turning (user decision, 2026-10-23). y and z are
  constant. No rotation anywhere.
- Use case: extract VELOCITY and ACCELERATION of the ego vehicle from the point cloud. The
  vehicle can drive forwards, drive backwards, stop, and drive at different speeds.
  (Position is the base signal they come from. Direction of travel, turns, sharp-turn and
  other events, and clip candidates are DROPPED.)
- Config: YAML files in config/, loaded and validated by core/config.py (pydantic).
  Env var may override the warehouse path.
- Lake: plain Parquet (PyArrow), Hive-style folders partitioned by drive, behind one
  Lake class (partition swap, read, list). DuckDB for SQL.
- API: Python SDK (VLClient) + SQL. No web service (FastAPI is "coming soon").
  Confirmed by the user on 2026-10-23. VLClient is built in Module 3 and reads through
  core/lake.py, which Module 2 builds.
- Ground truth is stored outside the warehouse and read only by the evaluation step.
- Every file is hashed (SHA-256). manifest.json lists the scenario hash and the hash of
  every file. A lineage table links scenario hash -> file hashes -> row counts, so data
  can be tied to its scenario and checked against ground truth.
- Quality: Typer CLI, pytest + hypothesis, ruff, mypy, src layout, Python 3.11,
  Windows PowerShell (python -m ... only).

OVERALL SHAPE
 config/*.yaml -> core/config.py (pydantic)
 [1 GENERATOR] -> data/raw/<hash12>/{frames.parquet, ground_truth.parquet, manifest.json}
   -> [2 ETL] (verify hashes, validate VL-001..006, reduce to keypoints) -> lake
   -> [3 USE-CASE] (velocity, acceleration from the lake) -> lake
   -> SDK (+SQL) -> [4 BI: one Streamlit app, 3 tabs]
 core/ = config loader, Arrow schemas, Lake, hashing. Dependencies point one way:
 core -> 1 -> 2 -> 3 -> 4.

MODULE 1: DATA GENERATOR
- Input: Scenario (pydantic, saved as YAML): start (x, y, z in cm; speed, default 0 cm/s),
  seed, and a motion profile = list of segments of two types:
    move(duration_s, end_speed_cm_s): speed changes in a straight line from the current
      speed to end_speed (signed; equal speeds = constant speed; sign change = reversal).
    stop(duration_s): speed held at 0.
  Durations are in seconds and validated to a whole number of frames (multiple of 1/16 s).
  Validation rejects a move whose start and end speed are both 0 (use stop).
- Output: full point cloud per frame (1 m cube, 100x100x100 lattice = 1,000,000 points,
  1 cm apart, from 0 to 99 cm, fixed order, int32 cm, 16 fps,
  timestamp_ns = frame_id * 62,500,000),
  ground_truth.parquet (per-frame x position, velocity, acceleration), manifest.json.
- Tech: numpy, pydantic, PyYAML, PyArrow, hashlib, Typer.
- UI: minimal form in the Streamlit Generate tab (start values, editable segment table,
  preview plot, Generate button). CLI calls the same function.
- Simulator validation (two-way): infer_track(frames) recovers per-frame position and
  velocity from centroids; fit_segments(track) recovers the typed segment list. hypothesis
  tests check infer(generate(s)) ~= s with MEASURED tolerances. Also: a 1 cm x-move shifts
  every point by exactly (1,0,0).
- Fault-injection helper (drop frames, corrupt a frame, shift timestamps) for ETL tests.
- Noise: out of scope. The only error is integer-cm rounding of the points.

MODULE 2: LOADER / ETL
- Verify file hashes against the manifest; validate each frame with error codes
  VL-001 missing frame, VL-002 timestamp gap, VL-003 duplicate frame, VL-004 corrupt point
  cloud, VL-005 schema mismatch, VL-006 physically impossible motion.
- Reduce each frame to critical points: 8 cube corners + centroid (9 points), chosen by a
  list in YAML. Reason for corners: fixed spacing is a rigid-shape check (VL-004).
- Assumption: sensor point order is fixed, so keypoints are picked by index.
- Tech: pandas, numpy, PyArrow, DuckDB, rule registry.
- Lake tables: keypoints, quarantine, lineage. Idempotent re-ingest via partition swap.

MODULE 3: USE-CASE ALGORITHM
- Queries keypoints through the SDK. Computes velocity (differences of the centroid x over
  1/16 s, signed) and acceleration (rate of change of velocity). Smoothing or window fits
  are allowed because per-frame differences of rounded points are noisy.
- Output: motion table in the lake.
- Evaluation: join with ground truth by scenario hash; velocity and acceleration error vs
  measured tolerances. The only place that reads ground truth.

MODULE 4: BI
- One Streamlit + Plotly app, three tabs: Generate, Clean (quality by error code, kept vs
  dropped), Analyze (estimated vs true velocity and acceleration timelines, error
  metrics). Uses SDK and module functions only. Scenario-hash badge on each tab.

  of the Module 1 plan.
- Noise: out of scope.
- Ground truth: per-frame x position, velocity and acceleration. No event labels.
- UI scope for Module 1: the Generate tab only, as a self-contained function with a small
  standalone runner. The three-tab shell is built in Module 4.
- Approved extra sources: official docs of pydantic, PyYAML, Typer, hypothesis, Python
  hashlib/json.
- Segments: move + stop (see Module 1). No turn, no cruise/brake types.
- Point sample: REPLACED on 2026-10-24, see "FULL DENSITY" below. (First plan: 10x10x10
  lattice, 1,000 points from 0 to 99 cm; the 8 corners are lattice points, fixed order,
  no seed needed. That part still holds.)
- Scenario hash: SHA-256 of canonical JSON of the validated scenario (sorted keys, fixed
  number formatting) + seed.
- infer_scenario: both, in two steps (infer_track, then fit_segments).
- Manifest file hashes: SHA-256 of the file bytes on disk.
- Drive folder: data/raw/<first 12 hex of scenario hash>/ ; the manifest keeps the full
  64-hex hash and the ETL checks it.
- Start speed: scenario start block has speed, default 0 (the drive starts at rest).
- Durations: seconds, validated to whole frames.

MEASURED ON THE 10x10x10 LATTICE, BEFORE THE FULL-DENSITY CHANGE (history; NOT re-measured at

FULL DENSITY (user decision, 2026-10-24)
- The generator produces the real density of the assignment's example: a 1 m cube of
  100^3 = 1,000,000 points per frame, 1 cm apart (12,000,000 bytes per frame). The PDF
  allows fewer frames ("save 1000 frames for example"), not thinner frames, so the
  10x10x10 sample above was our own choice and is replaced. Config: points_per_axis = 100.
- Corners (x-major order): indices 0, 99, 9,900, 9,999, 990,000, 990,099, 999,900 and
  999,999 (compute them from cube_lattice, do not hard-code). Module 2 picks keypoints by
  these indices; VL-004 (one point removed) is 999,999 points = 11,999,988 bytes.
- Storage: zstd instead of snappy (a 2-frame test: snappy 8,048,769 bytes, zstd 549,552
  bytes). Repeated on the real 1,000-frame demo drive (2026-10-24, measured):
  snappy 4,024,944,648 bytes, zstd 287,134,433 bytes for frames.parquet. One Arrow binary
  array holds at most
  2,147,483,647 bytes = 178 full frames, so frames are built and written in batches of
  about 50 frames and streamed to the parquet file (row groups of about 50 rows). The
  in-memory generate() and write_drive stay for small drives and tests; they refuse a drive
  over 1 GiB of points (MAX_IN_MEMORY_BYTES, more than 89 frames at full density), and
  generate_to_disk (the CLI and the Generate tab) streams without that limit.
- Demo: keep the 1,000-frame demo at full density (about 12 GB raw, computed: 1,000 frames
  x 12,000,000 bytes; a scenario may have at most 2,000 frames, about 24 GB raw). Measured
  2026-10-24: 75.1 s, peak working set 2,859 MiB (scratch script); the generate command took
  81 s (source: .claude/run-proofs/FULL-DENSITY-iter2.log); the fresh-clone time of
  2026-10-25 is in RELEASE_NOTES, Usage.
- Hash: the body (size_cm, points_per_axis) joins the scenario hash, so each density has
  its own hash and folder. This changed the demo hash (it was c8f597af59a6 before the change; now bf394b9bfb42). Core files that
  Module 2 and 3 import are changed only after agreeing with the Module 2 session.
- infer_scenario also recovers start y and z from the frames.
- Manifest: Module 2 asked for a self-describing manifest (body size_cm and points_per_axis;
  key names were not decided then). Done: schema_version 2 with a body block (size_cm,
  points_per_axis).
- Tests use a small-lattice config (10 per side) except tests of the full density.
- Tolerances in the MEASURED block were measured on the 10x10x10 lattice. At full density the
  roundtrip command (2026-10-25, fresh clone) printed boundary error 4 frames, duration error
  5 frames and end-speed error 24.4 cm/s, within the limits; the position and velocity errors
  were not re-measured there. The task file is .claude/plans/followups/full-density.md; it runs after
  TASK-6 (fault injection) and before TASK-7 (Generate tab).
