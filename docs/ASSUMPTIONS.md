You confirmed the top speed as 322 km/h (8,944 cm/s) on 2026-10-23, and I rounded it up to 9,000 cm/s. | Change `max_speed_cm_s` in `config/etl.yaml`. A higher value misses small teleports. |
| M2-A2 | The generator's `Teleport` fault moves only its own frame. The generator session confirmed this on 2026-10-23. One teleport makes two bad jumps (into the frame and out of it), but the rule compares with the last accepted frame, so only the teleported frame is flagged. | The fault is described as "a frame jumps by dx_cm". | If it shifts every later frame, the "compare with the last accepted frame" rule would quarantine all of them. The rule must change. |
| M2-A3 | VL-006 compares a frame's centroid with the last accepted frame, scaled by the frame number gap, using the straight-line distance in x, y and z. | A dropped or rejected frame must not make its neighbour look like a jump. | Neighbours of quarantined frames could be flagged wrongly. |
| M2-A4 | No ETL rule tests acceleration per frame. | Per-frame acceleration error (452 cm/s^2) is larger than the signal. | Good drives would be flagged. |
| M2-A5 | Whole-drive failures that are not VL codes (hash, manifest, schema version, folder name, a frame number outside 0 to frame_count-1) use the code `INTEGRITY`. | The six VL codes describe frames. | Another name for the same rows; only the document changes. |
| M2-A6 | The `ingest` command exits 0 when a drive was ingested, even if some frames were quarantined, and exits 1 when the drive was rejected. | Quarantine is normal operation. A rejected drive is a failure. | Scripts that expect non-zero on any quarantine need a flag. |
| M2-A7 | The lineage table holds no wall-clock time. | A re-ingest then leaves the lake byte-identical. | Adding `ingested_at` loses the byte-identical check. |
| M2-A8 | Keypoint x, y and z are stored as float64 centimetres. | The centroid has .5 values; corners are whole numbers and fit exactly. | Mixed types per keypoint would complicate the table. |
| M2-A9 | ETL settings live in `config/etl.yaml`, loaded by `etl/config.py`. The cube size and fps come from the core config and the manifest. | It avoids editing the Module 1 config file. | Merge the settings into `core/config.py` later. |
| M2-A10 | The ETL imports `generator.body.cube_lattice` to know the expected lattice. | One source of truth for the lattice. Imports still point one way. | A copy in the ETL could drift from the generator. |
| M2-A11 | A re-ingest swaps the keypoints, quarantine and lineage partitions one after another, not as one atomic step. | Plain Parquet folders have no multi-table commit. | A crash between swaps leaves mixed tables until the drive is ingested again. |
| M2-A12 | Two frames with the same frame number are identical copies only if their timestamp and points hash both match. | A different timestamp means a different record. | A looser rule would keep a repeat with a bad clock. |
| M2-A13 | Frames in the file may be out of order. The ETL orders them by frame number before VL-006. | A duplicate may be appended at the end. | A sorted-file assumption would give false jumps. |
| M2-A14 | The ETL never opens `ground_truth.parquet`. The lineage row stores the file's hash from the manifest so evaluation can tie to it. | Only the evaluation step may read ground truth. | Leakage into the ETL would make the checks meaningless. |
| M2-A15 | The Lake is single-writer. Two swaps on the same lake folder at the same time are not supported. | Plain Parquet folders have no locking, and the ETL loads drives one after another. | Parallel loading needs a lock file or a table format with commits (for example Iceberg). |
| M2-A16 | After a failed restore, the old partition stays in `<lake>/_swap/old-<token>` and is never deleted automatically. A later swap only removes `new-*` folders older than one hour. | A review showed that deleting `old-*` could destroy the only copy of a partition. | A leftover `old-*` folder after a successful swap (a locked file) is harmless but also never cleaned up; remove it by hand. |
| M2-A17 | DuckDB views over the lake turn hive partitioning off and add the drive id as a literal column. | With auto-detection, DuckDB read `key=value` segments of the lake folder's own path (for example `env=prod`) as extra columns, and a numeric-looking id as a number. | A different DuckDB version may behave differently; the tests `test_view_with_hive_like_segments_in_root` and `test_duckdb_numeric_only_drives_stay_strings` would show it. |
| M2-A18 | The Parquet write options are pinned (version 2.6, snappy, data page 1.0, dictionary on, statistics on, row group 65,536 rows), so identical input and batch boundaries give identical bytes. | Needed for a byte-identical re-ingest. The DuckDB and PyArrow docs do not state it, so a test (`test_swap_replaces_and_is_idempotent`) proves it. | Bytes can differ across pyarrow versions; the footer stores the library version. |
| M2-A19 | The dependency `duckdb>=2.0,<3` is added to the runtime dependencies. | The Lake's query views need it. The upper bound avoids an unreviewed major version. | Raise the bound after testing a new major version. |
| M2-A20 | The ETL config mirrors `core/config.py`: with no path it reads `config/etl.yaml` or falls back to the built-in defaults when that file is absent; an empty file means defaults; an explicit missing path is an error. `keypoints` has a built-in default (the nine keypoints) identical to the YAML file. | The Module 1 loader works this way, and the plan did not say. | A required `keypoints` field would make an absent file an error. |
| M2-A21 | A keypoint name uses only letters, digits and `_`, up to 64 characters. A keypoint index and the schema versions must be real integers. | The name becomes a value in the keypoints table and may later become a column or file name; YAML `true` or `9.0` would otherwise be silently coerced. | A name with other characters needs the pattern widened. |
| M2-A22 | Config bounds: `max_speed_cm_s` at most 100,000, `chunk_mib` at most 1,024, at most 256 keypoints and 16 schema versions. | A hand-edited config could otherwise ask for absurd memory. | Raise a bound in `etl/config.py` if a real case needs it. |
| M2-A23 | `extract_keypoints` accepts any integer dtype and refuses floats (including NaN). The centroid is the float64 mean. | The generator writes int32 cm; a float array means something upstream is wrong. | A float source would need an explicit rounding step first. |
| M2-A24 | Corner keypoints are named by bits (x, y, z) and their lattice index is derived from the drive's points per axis n, so the same keypoint list works at 10 or 100 points per axis (replaces the fixed 10 x 10 x 10 indices after the full-density decision of 2026-10-24). | The generator will write 1,000,000 points per frame. | A lattice that is not a cube of points per axis cannot be handled by the corner kind. |
| M2-A26 | Chunks are sized in MiB of int32 xyz point data (`chunk_mib`, default 128), not in frames. | At 12 MB per frame a fixed frame count (256 frames = 3 GB) would exhaust memory on a 15.7 GB machine. | Lower `chunk_mib` if memory is tight. The Parquet row group the generator writes (about 50 frames, 600 MB) is read whole, so memory is at least that. |
| M2-A27 | Until the generator adds body keys to the manifest, `etl/body.py` takes points per axis from the integer cube root of `points_per_frame` and `size_cm` from the core config. | The manifest has no body keys yet; the generator will send the exact names (and bump `schema_version`) before it edits core. | A manifest with body keys must take precedence; only `drive_body` changes. |
| M2-A25 | `tests/etl/` has an `__init__.py`, and `tests/core/` has none. | `tests/etl/test_config.py` and `tests/core/test_config.py` share a file name; without the package marker pytest fails at collection. | Rename one file and drop the marker. |
| M3-A1 | The motion position keypoint is named `centroid`; that name comes from `config/etl.yaml` (the keypoints list), and `position_keypoint` in `config/motion.yaml` must match a name there. | The Module 3 algorithm reads one keypoint per frame from the lake. | If the ETL renames the keypoint, `config/motion.yaml` must change with it; the config loader does not check the name against the ETL config. |
| M3-A2 | The defaults in `config/motion.yaml` (window 16 frames, order 2, 5 minimum points, 4 frame gap, tolerances 20 cm/s and 60 cm/s^2; config values, not measured) are provisional until the TASK-3 sweep replaces them. | They are starting points, not measured values. | Results before the sweep depend on guesses; re-run after the sweep. |
| M3-A3 | The estimator window for frame i holds the samples within `window_frames`/2 frame intervals either side of t_i (centred; one-sided at the first and last frames, so edge windows hold about half the points). | A centred window gives an unbiased fit inside the clip; the edges still get an estimate. | Edge estimates are noisier than interior ones; narrow or widen `window_frames` if the edges matter. |
| M3-A4 | Gap rule: a window is rejected when any two consecutive samples in it are more than `max_gap_frames` frame intervals apart (real timestamps; a tolerance of 1e-6 of a frame interval is added to both the window edges and this gap check), or when it holds fewer than `min_points` samples. A gap of exactly `max_gap_frames` is accepted. | Fits across long holes are extrapolation, not measurement. | A tighter limit gives more NaN; a looser one lets the fit bridge occlusions. |
| M3-A5 | NaN in the estimator outputs means "no estimate", not zero or a failure; `n_points` still holds the window count. Callers must skip or report NaN frames rather than treat them as zero motion. | Missing data must not look like standing still. | Averaging over NaN without masking gives NaN results. |
| M3-A6 | `n_points` is the count of samples inside the window, and it is reported even when the output is NaN. The window spans `window_frames`/2 frame intervals either side of t_i, so an even `window_frames` gives `window_frames` + 1 points in a full interior window, and an odd one gives `window_frames` points. | The count lets callers see why a frame has no estimate. | Reading `n_points` as the number of valid fits, or as exactly `window_frames`, is wrong. |
