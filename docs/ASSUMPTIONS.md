| A63 | Parquet files use zstd (it replaces snappy) with row groups of 50 rows (frames and ground truth); `BATCH_FRAMES` and `ROW_GROUP_ROWS` are both 50, so the streaming writer and `write_drive` give identical bytes. Measured on 1,000 frames at 1,000,000 points: zstd 287,134,433 bytes, snappy 4,024,944,648 bytes (`.claude/run-proofs/FULL-DENSITY-measure.log`). The demo `frames.parquet` from the measurement run (`FULL-DENSITY-measure.log`) is 287,134,433 bytes. | A reader (pyarrow, DuckDB) must load a whole row group: 50 frames = 600 MB, not 12 GB. Module 2 asked for about 50. | Smaller row groups cost more metadata; a different codec changes only the Parquet bytes. |
| A64 | The manifest is `schema_version` 2: a required nested `body` block (`size_cm`, `points_per_axis`, both bounded: `size_cm` 1 to 2,147,483,647, `points_per_axis` 1 to 1,000,000), and `points_per_frame` must equal `points_per_axis` cubed. A version 1 manifest (no `body`) fails validation. `BodyConfig.points_per_axis` now defaults to 100 and `config/default.yaml` says 100; tests use a 10-per-axis `small_config` fixture. | Agreed with the Module 2 session on 2026-10-24. | Module 3 tests that rely on the old default of 10 must pass a body. |
| A65 | `BodyConfig` is within the bounds of `BodyInfo` in the manifest: `points_per_axis` is 1 to 1,000,000 in `BodyInfo` and `BodyConfig` is stricter (2 to 1,000,000); the `size_cm` bounds are the same (1 to 2,147,483,647). So a config that loads is within the manifest bounds. That does not make every loaded config writable: `points_per_axis` above `size_cm` is still refused, early, by `cube_lattice`. `cube_lattice` raises ValueError, before allocating, for `points_per_axis` above 1,000,000, for a frame of `points_per_axis`^3 x 12 bytes at or above the Arrow single-binary limit of 2^31 bytes (so `points_per_axis` of 564 or more; the shipped 100 is 12,000,000 bytes), and for `size_cm` - 1 above the int32 range (it used to wrap silently). `infer_track` refuses a config whose 50-frame batch would not fit one Arrow binary array, before it builds the lattice. | A config past the bounds used to fail late, after the streaming write, and a huge `points_per_axis` could run out of memory in `roundtrip`. | A body larger than these bounds needs the manifest and config bounds raised together. |
| A66 | `drive_hash` accepts a body value only if it is a whole number: 100 and 100.0 give the same hash, 100.5 (and nan or inf) raises ValueError. `scenario_hash(scenario)` without a body is not a drive hash and must not name a drive folder. | `int()` truncated 100.5 to 100, which gave it the hash and folder of the 100 body. | A caller that passed a fractional body now gets an error instead of a silent collision. |
| A67 | `generate_to_disk` runs `verify_drive` on the temp folder before the swap, so a drive that fails verification never replaces a good folder. The files are still hashed twice (once to build the manifest, once to verify); verification is an independent re-read and is kept, so the demo's 287 MB file is read twice. | A bad drive used to replace the good one first and fail after. | Skipping verification would save one full hash pass but would no longer detect a bad write. |
| A68 | `generate()` and `write_drive` raise ValueError when a drive's points are over `MAX_IN_MEMORY_BYTES` = 1 GiB (2^30 bytes): up to 89 full-density frames (89,478 at 10 points per axis) are allowed; one more is refused. The message points to `generate_to_disk`. `generate()` computes the size from the config and refuses before building anything; `write_drive` checks the size of the drive it is given, which is already built, so it limits what is written but does not prevent that allocation. | The demo would need about 12 GB in memory; 1 GiB keeps tests and small scenarios working and refuses surprises. | A caller that needs a bigger in-memory drive can raise `drive.MAX_IN_MEMORY_BYTES`. |
| A69 | No performance change to `place_body` or `infer_track`. Measured at full density (one run, `.claude/run-proofs/FULL-DENSITY-1-measure.log`): `place_body` 42.0 ms per frame, 50-frame batch generation 59.1 ms per frame, `infer_track` 17.8 ms per frame. At the 2,000-frame cap that is about 118 s plus 36 s (scaled, not run). | The best saving is about 61 s at most (calculated: 30.7 ms x 2,000 frames), and a faster `place_body` would change the rounding at x.5 ties, which must not change. | Revisit if the cap is raised. |
